# STM32F407 + FreeRTOS 学习笔记

这份笔记记录项目学习过程中提出的问题、对应知识点、代码位置和实机证据。后续问题按日期继续追加。

## 2026-08-13：第一步为什么只做一个最小 FreeRTOS 工程？

### 我的问题

1. 当前代码的主要功能是什么？
2. 我可以从中学到什么？
3. 为什么第一步不直接加入 LCD、触摸和以太网？

### 简要答案

当前代码不是最终产品，而是一个“最小可验证基础平台”。它证明下面这条最基础的软件链路能够独立工作：

```text
复位 -> 时钟初始化 -> USART1 初始化 -> 创建 FreeRTOS 对象
     -> 创建任务 -> 启动调度器 -> 任务间传递消息 -> 串口输出
```

如果这条链路不稳定，后面加入 LCD、网络、CAN 后发生故障，就无法判断问题属于底层启动、RTOS，还是某个外设。因此先建立一个故障范围很小的基线。

### 当前代码的功能

#### 1. 初始化 MCU

- 使用开发板 8 MHz HSE；
- PLL 将系统时钟配置为 168 MHz；
- 初始化 USART1：PA9/PA10，115200-8-N-1。

代码位置：`Core/Src/main.c` 中的 `SystemClock_Config()` 和 `MX_USART1_UART_Init()`。

#### 2. 创建 FreeRTOS 对象

- `log_queue`：容量为 8 的消息队列；
- `health_events`：保存模块是否启动成功的事件位；
- FreeRTOS Heap 总大小为 32 KiB，使用 `heap_4.c` 管理。

代码位置：`Core/Src/main.c`、`Core/Inc/FreeRTOSConfig.h`。

#### 3. 运行三个任务

| 任务 | 优先级 | 当前作用 |
|---|---:|---|
| `health_task` | 4 | 每秒读取健康状态和剩余 Heap，组成一条日志消息 |
| `logger_task` | 3 | 阻塞等待队列消息，收到后通过 USART1 输出 |
| `ui_task` | 1 | 当前只设置启动成功标志并周期休眠，为以后 LCD 任务预留 |

这里故意让 `health_task` 不直接操作串口，而是把消息放入 Queue，再由 `logger_task` 统一输出。这是在练习任务职责分离和任务间通信。

#### 4. 输出健康状态

实机输出示例：

```text
[      1000] health bits=0x07 heap=25320
```

- `1000`：FreeRTOS Tick；当前 1 Tick = 1 ms；
- `0x07`：二进制 `111`，表示 boot、logger、ui 三个状态位都已设置；
- `25320`：FreeRTOS 当前剩余 Heap 字节数；数值持续稳定是好现象。

第一次出现 `0x01` 随后变为 `0x07`，表示 `health_task` 第一次运行时，另外两个任务还没来得及设置自己的启动位。这展示了多任务启动顺序不是固定的。

#### 5. 捕获严重错误

- 创建 Queue、Event Group 或任务失败会进入 `Error_Handler()`；
- FreeRTOS 动态内存分配失败会调用 `vApplicationMallocFailedHook()`；
- 任务栈溢出会调用 `vApplicationStackOverflowHook()`。

这些钩子目前只停机，后续会加入故障信息保存和串口输出。

### 这一阶段可以学到什么

1. MCU 从复位到 `main()` 的启动过程；
2. HSE、PLL、SYSCLK、APB 时钟的基本关系；
3. FreeRTOS 调度器和 Tick 的作用；
4. 任务、优先级、阻塞与周期运行；
5. Queue 如何安全地在任务之间传递数据；
6. Event Group 如何用位表示多个模块状态；
7. FreeRTOS Heap 与任务栈不是同一个概念；
8. 如何用串口和 ST-LINK 形成可观察、可调试的证据链；
9. 如何通过 Git 功能分支隔离尚未验收的改动。

### 第一阶段的完成标准

- 串口每秒稳定输出；
- `health bits` 稳定为 `0x07`；
- Heap 长时间保持稳定；
- 不发生 HardFault 或意外复位；
- 能输出每个任务的栈高水位；
- 能人为制造一个故障，并确认监控机制能够发现它。

满足这些条件后，再把 ILI9806、CST716 和 LAN8720A 逐项加入。每增加一个模块，都能与这个最小基线比较，从而快速确定故障由哪个增量引入。

## 2026-08-15：增加 FreeRTOS 资源监控、IWDG 与故障注入

### 本阶段实现

- `uxTaskGetStackHighWaterMark()`：输出 `health/logger/ui` 三个任务的栈高水位，单位是 FreeRTOS 栈 word；数值越小表示越接近栈耗尽。
- `xPortGetMinimumEverFreeHeapSize()`：记录运行以来 FreeRTOS Heap 的历史最低剩余量。
- `qdrop`：统计向满 Queue 发送失败而丢弃的日志消息。
- IWDG：使用 LSI，约 3 秒超时，由 `health_task` 每秒刷新；启动时读取并打印 IWDG 复位标志。
- 任务心跳监督：`logger` 每成功输出一条消息、`ui` 每次周期运行都会更新心跳；`health_task` 在启动宽限期后检查心跳，只有监督正常才刷新 IWDG。
- 故障注入由 CMake `DIAG_FAULT_MODE` 控制，默认 `none`，可选 `queue`、`watchdog` 或 `logger`。

### 验收方法

`queue` 模式在第 5 秒快速填充日志队列，预期 `qdrop` 增加；`watchdog` 模式在第 5 秒停止刷新 IWDG，预期约 3 秒后复位，重启日志出现 `reset cause=IWDG`；`logger` 模式让 logger 心跳停止，预期 supervisor 输出故障并停止刷新 IWDG，随后复位。故障测试固件只用于验证，验收后必须恢复 `DIAG_FAULT_MODE=none`。

### 我对 CMake 命令参数的疑问

```bash
cmake --preset debug -DDIAG_FAULT_MODE=queue
cmake --build --preset debug
cmake --build --preset debug --target flash
```

逐项理解：

1. `cmake --preset debug`：读取 `CMakePresets.json` 的 `debug` 预设，生成 Debug 配置和 Ninja 构建文件。
2. `-DDIAG_FAULT_MODE=queue`：在 CMake 配置阶段设置缓存变量。项目根据它把 `DIAG_FAULT_MODE` 编译宏设为队列故障注入模式。
3. `cmake --build --preset debug`：调用已经生成的 Ninja 文件进行编译和链接，只生成固件，不烧录。
4. `--target flash`：选择名为 `flash` 的自定义目标；它调用 STM32CubeProgrammer 和 ST-LINK 将 ELF 烧录到 MCU 并复位。

模式的含义：

- `none`：正常运行；
- `queue`：约第 5 秒制造队列拥塞，观察 `qdrop`；
- `watchdog`：约第 5 秒停止刷新 IWDG，观察自动复位和 `reset cause=IWDG`。

`-D` 参数会保存在 `build/debug/CMakeCache.txt`，不是只对当前命令临时有效。因此测试完成后要显式恢复正常模式：

```bash
cmake --preset debug -DDIAG_FAULT_MODE=none
cmake --build --preset debug
```

## 2026-08-13：Windows 下应该选择哪套 STM32 开发环境？

### 结论

本项目规定 Git Bash 为日常命令终端，不额外安装 MSYS2。Git Bash 已经能够运行 Git、Shell 脚本和 Windows `.exe`；STM32 裸机工程不需要 MSYS2 提供的大量 Unix 软件包。

采用的工具链是：

```text
Git Bash
  -> CMake Presets
  -> Ninja
  -> ARM GCC（STM32CubeIDE 内置）
  -> ELF/BIN/MAP
  -> STM32CubeProgrammer CLI
  -> ST-LINK
```

`tools/env.sh` 在每个 Git Bash 会话中自动查找 CubeIDE 内置的 ARM GCC、GDB、CubeProgrammer 和 ST-LINK GDB Server，并临时加入 PATH。它不永久修改 Windows 系统 PATH。

选择 CMake 的主要目的不是让固件功能改变，而是让构建配置结构化、可重复，并方便未来接入 VS Code、静态分析、单元测试和 CI。

## 2026-08-17：节点 6——FreeRTOS UI 事件层

### 我学到的内容

- `input_task` 负责触摸采集，`ui_task` 负责 LCD 刷新，任务之间用 `ui_event_queue` 传递结构化事件；这样输入驱动不会直接依赖显示代码。
- EXTI 中断只做清中断和任务通知，软件 I2C 读取与 LCD 绘图都在任务上下文完成，避免在 ISR 中执行耗时操作。
- `ulTaskNotifyTake()` 适合“中断唤醒任务”，超时参数又能保留周期轮询作为可靠性回退。
- `qdrop` 表示日志队列丢弃，`edrop` 表示 UI 事件队列丢弃，两者要分别观察；队列容量不是越大越好，必须配合丢包计数。
- `ui_task` 独占 LCD，其他任务不直接访问 FSMC，可以避免多个执行上下文同时改写显示窗口。

### 验收目标

节点 6 烧录后，串口健康位应从原来的 `0x07` 变为四任务的 `0x0f`，并保持 `qdrop=0`、`edrop=0`、`supervisor=ok`、`wd=ok`；LCD 状态页显示 Heap、健康位、最近触摸坐标和事件计数。

## 2026-08-23：节点 7——CAN 板级合同

原理图确认本板 CAN 区域使用 CAN1 和 U8 `TJA1040` 收发器：`PA11=CAN1_RX`、`PA12=CAN1_TX`，总线从 P7 的 `CANH/CANL` 引出，R18 为 120 Ω 终端。STM32F407 虽然还提供 PB8/PB9、PD0/PD1 等 CAN1 复用映射，但实际工程应优先遵循原理图网络，而不是只看 MCU 复用表。

CAN 的“外设初始化成功”不等于“总线通信成功”。要验证 ACK、错误计数和 Bus-Off 恢复，至少需要 USB-CAN 或第二个 CAN 节点；没有外部节点时只能先做内部回环和寄存器级验证。

## 2026-08-23：节点 8——CAN1 内部回环

- 使用 `CAN_MODE_SILENT_LOOPBACK` 时，CAN 控制器在芯片内部把发送帧送回接收 FIFO，不需要外部 CAN 节点，也不代表 CANH/CANL 电气链路已通过。
- 当前配置为 PCLK1=42 MHz、Prescaler=6、14 个时间量子，即 500 kbit/s；标准帧 ID 为 `0x321`，每秒发送一次。
- RX FIFO0 中断只负责进入 HAL IRQ 处理并通知 `can_task`；`HAL_CAN_GetRxMessage()` 放在任务上下文，避免在 ISR 中做较重的读取和日志格式化。
- `can=TX/RX` 记录发送与接收计数，`irq` 记录 FIFO0 中断次数；健康位新增 `EVT_CAN_OK`，因此稳定值预期从 `0x0f` 变为 `0x1f`。
- 本次实机日志中反复出现 `reset cause=IWDG`、`can=0/0`、`irq=0`，说明只能证明初始化函数返回成功，不能证明回环任务已经完成收发；现象优先按“任务/中断链路卡住”排查，而不是把初始化日志当作验收结果。
- 修复版本对 FIFO0 pending 中断做了防止持续触发的保护，并补上 CAN1 SCE 错误中断入口；重新验证时必须观察至少 5 秒，确认不再复位且 `can`、`irq` 持续递增。
- 本次寄存器日志显示 `apb1=0x12000000`（CAN1 时钟位已置位），但 `mcr=0x00010040` 的 `INRQ=0` 后，`msr=0x00000009` 仍保持 `INAK=1`，并带有 `WKUI=1`；因此问题在 CAN 控制器退出初始化握手，而不是发送帧格式或日志队列。
- 为隔离板上 PA11/PA12 及收发器影响，回环模式改为 `CAN_MODE_SILENT_LOOPBACK`，并在启动前清除 CAN 调试冻结位和旧唤醒标志。
- 2026-08-24 的原理图复核确认 P9 是 CAN/USB 二选一跳帽：中间为 PA11/PA12，上侧连接 U8 的 CAN_RX/CAN_TX，下侧连接 USB D-/D+。bxCAN 退出初始化前要在 RX 上检测到隐性高电平；若 P9 接在 USB 侧或 RX 悬空/被拉低，就会出现 `MCR.INRQ=0` 但 `MSR.INAK=1` 的启动超时。
- 2026-08-25 实机验收通过：连续 45 秒得到 `health bits=0x1f`、`can=45/45`、`irq=45`、`cerr=0`、`qdrop=0`、`edrop=0`、`supervisor=ok`、`wd=ok`，并逐秒收到 ID `0x321` 的回环帧。
