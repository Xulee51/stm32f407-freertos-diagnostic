# STM32F407 + FreeRTOS 学习笔记

这份笔记记录项目学习过程中提出的问题、对应知识点、代码位置和实机证据。后续问题按日期继续追加。

## 2026-08-13：第一步为什么只做一个最小 FreeRTOS 工程？

### 我的问题

1. 当前代码的主要功能是什么？
2. 我可以从中学到什么？
3. 为什么第一步不直接加入 LCD、触摸和以太网？

### 简要答案

当前代码不是最终产品，而是一个“最小可验证基础平台”。它证明下面这条最基础的软件链路能够独立工作：

```text
复位 -> 时钟初始化 -> USART1 初始化 -> 创建 FreeRTOS 对象
     -> 创建任务 -> 启动调度器 -> 任务间传递消息 -> 串口输出
```

如果这条链路不稳定，后面加入 LCD、网络、CAN 后发生故障，就无法判断问题属于底层启动、RTOS，还是某个外设。因此先建立一个故障范围很小的基线。

### 当前代码的功能

#### 1. 初始化 MCU

- 使用开发板 8 MHz HSE；
- PLL 将系统时钟配置为 168 MHz；
- 初始化 USART1：PA9/PA10，115200-8-N-1。

代码位置：`Core/Src/main.c` 中的 `SystemClock_Config()` 和 `MX_USART1_UART_Init()`。

#### 2. 创建 FreeRTOS 对象

- `log_queue`：容量为 8 的消息队列；
- `health_events`：保存模块是否启动成功的事件位；
- FreeRTOS Heap 总大小为 32 KiB，使用 `heap_4.c` 管理。

代码位置：`Core/Src/main.c`、`Core/Inc/FreeRTOSConfig.h`。

#### 3. 运行三个任务

| 任务 | 优先级 | 当前作用 |
|---|---:|---|
| `health_task` | 4 | 每秒读取健康状态和剩余 Heap，组成一条日志消息 |
| `logger_task` | 3 | 阻塞等待队列消息，收到后通过 USART1 输出 |
| `ui_task` | 1 | 当前只设置启动成功标志并周期休眠，为以后 LCD 任务预留 |

这里故意让 `health_task` 不直接操作串口，而是把消息放入 Queue，再由 `logger_task` 统一输出。这是在练习任务职责分离和任务间通信。

#### 4. 输出健康状态

实机输出示例：

```text
[      1000] health bits=0x07 heap=25320
```

- `1000`：FreeRTOS Tick；当前 1 Tick = 1 ms；
- `0x07`：二进制 `111`，表示 boot、logger、ui 三个状态位都已设置；
- `25320`：FreeRTOS 当前剩余 Heap 字节数；数值持续稳定是好现象。

第一次出现 `0x01` 随后变为 `0x07`，表示 `health_task` 第一次运行时，另外两个任务还没来得及设置自己的启动位。这展示了多任务启动顺序不是固定的。

#### 5. 捕获严重错误

- 创建 Queue、Event Group 或任务失败会进入 `Error_Handler()`；
- FreeRTOS 动态内存分配失败会调用 `vApplicationMallocFailedHook()`；
- 任务栈溢出会调用 `vApplicationStackOverflowHook()`。

这些钩子目前只停机，后续会加入故障信息保存和串口输出。

### 这一阶段可以学到什么

1. MCU 从复位到 `main()` 的启动过程；
2. HSE、PLL、SYSCLK、APB 时钟的基本关系；
3. FreeRTOS 调度器和 Tick 的作用；
4. 任务、优先级、阻塞与周期运行；
5. Queue 如何安全地在任务之间传递数据；
6. Event Group 如何用位表示多个模块状态；
7. FreeRTOS Heap 与任务栈不是同一个概念；
8. 如何用串口和 ST-LINK 形成可观察、可调试的证据链；
9. 如何通过 Git 功能分支隔离尚未验收的改动。

### 第一阶段的完成标准

- 串口每秒稳定输出；
- `health bits` 稳定为 `0x07`；
- Heap 长时间保持稳定；
- 不发生 HardFault 或意外复位；
- 能输出每个任务的栈高水位；
- 能人为制造一个故障，并确认监控机制能够发现它。

满足这些条件后，再把 ILI9806、CST716 和 LAN8720A 逐项加入。每增加一个模块，都能与这个最小基线比较，从而快速确定故障由哪个增量引入。

## 2026-08-13：Windows 下应该选择哪套 STM32 开发环境？

### 我的问题

1. 能否规定只在 Git Bash 中执行开发命令？
2. 是否还需要安装 MSYS2？
3. 当前编译与烧录工具链是什么？
4. 如何迁移到 CMake？

### 结论

本项目规定 Git Bash 为日常命令终端，不额外安装 MSYS2。Git Bash 已经能够运行 Git、Shell 脚本和 Windows `.exe`；STM32 裸机工程不需要 MSYS2 提供的大量 Unix 软件包。

采用的工具链是：

```text
Git Bash
  -> CMake Presets
  -> Ninja
  -> ARM GCC（STM32CubeIDE 内置）
  -> ELF/BIN/MAP
  -> STM32CubeProgrammer CLI
  -> ST-LINK
```

`tools/env.sh` 在每个 Git Bash 会话中自动查找 CubeIDE 内置的 ARM GCC、GDB、CubeProgrammer 和 ST-LINK GDB Server，并临时加入 PATH。它不永久修改 Windows 系统 PATH。

选择 CMake 的主要目的不是让固件功能改变，而是让构建配置结构化、可重复，并方便未来接入 VS Code、静态分析、单元测试和 CI。
